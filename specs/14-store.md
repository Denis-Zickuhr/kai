# Spec 14: Kai Store

> **Status:** design, targeted at `1.0.0-beta.3`. Nothing implemented yet.

# Part A — Contract

## 1. Overview
The **Kai Store** is a place to find and install things made for Kai: commands,
folders, pipelines, whole projects, environment packs and execution profiles.
It is **not a server of ours**: the user picks one or more **providers**, and a
provider is any place that serves a catalog in the Store format — a Git repo, an
HTTP API, or a plain static text file (local or remote).

Installing is an **import**. It reuses the existing import code, creates
ordinary folders/commands, and nothing runs while installing.

### Principles (philosophy checks)
- **Opt-in network.** No provider is configured out of the box; with none, the
  Store has no menu entry and Kai never contacts anything. A provider is only
  contacted when the user opens the Store, refreshes it or installs from it.
- **No accounts, no telemetry, no counters.** An optional per-provider token is
  allowed for private stores; it lives with the other local secrets (mode 0600),
  never exported or synced.
- **Never self-acting.** No auto-update, no background check. Updates are found
  only when the Store is open or on click.
- **Not a package manager.** No dependency resolution between packages, no
  lockfiles. A package is self-contained.
- **Portable.** The package content is the formats Kai already reads
  (`kai.yml`, `kai_export`). The Store adds only a manifest and an index.

### Non-goals
Publishing through the app (upload, accounts), ratings/comments, download
counts, paid packages, automatic dependency installation, silent updates.

## 2. Providers
A provider is `{ id, name, kind, location, token?, trust, enabled }`, stored in
local settings (not exported).

| kind | `location` | How the catalog is read |
|---|---|---|
| `file` | a path or URL of a single `.yml`/`.json` **catalog file** | one read; the file lists every package inline (and may point to payloads by relative path/URL) |
| `repo` | a Git URL (`https://…/x.git`, or a `github.com/owner/repo` page) | reads `store.yml` + `index.json` over HTTPS (raw); falls back to a shallow clone when `git` exists and raw is unavailable |
| `api` | a base URL | `GET {base}/v1/index` etc. (§6) |

The user may type any location; Kai **suggests** the kind (`.git` or a known
forge host → repo; `.yml/.json/.yaml` or a local path → file; otherwise → api)
and the user can override it. "Test connection" fetches and validates the
catalog header and shows name, package count and signature state.

`trust` is one of `official | verified | community | custom`, set by the user
when adding; a first-time add shows one short warning that packages are code.
The official provider is *offered* in a first-run empty state of Settings →
Store as a one-click add; never added by default.

The three kinds expose **one logical contract** (§3–§5). `file` and `repo` are
static (the catalog is documents); `api` serves the same documents dynamically
and adds server-side search.

## 3. Catalog
### `store.yml` (provider header)
```yaml
store_format: 1
name: Acme Kai Store
description: { en: ..., pt: ... }
homepage: https://...
categories:
  - { id: deploy, name: { en: Deploy, pt: Deploy }, icon: rocket }
  - { id: git,    name: { en: Git } }
signing: { algorithm: ed25519, key: <base64 public key> }   # optional
index: index.json                                           # default
```
In a `file` provider the header and the `packages:` list live in the same file.

### Index (`index.json`)
One summary row per package, enough to render the grid without opening any
package. Generated by `kai store index`; never hand-written.
```json
{ "store_format": 1, "generated": "2026-11-06T12:00:00Z",
  "packages": [
    { "id": "acme/ship-to-staging", "kind": "pipeline", "name": "Ship to staging",
      "summary": { "en": "…", "pt": "…" }, "category": "deploy", "tags": ["git"],
      "latest": "1.2.0", "icon": "packages/acme/ship-to-staging/icon.png",
      "versions": [ { "version": "1.2.0", "kai_min": "1.0.0-beta.2",
                      "requires": ["pipelines"], "manifest": "…/1.2.0/package.yml",
                      "sha256": "…" } ] } ],
  "signature": "<base64 over the canonical index body>" }
```
Versions are listed with their compatibility so the grid can grey out
incompatible packages **without** fetching manifests. Cached locally with
ETag/If-Modified-Since; icons and screenshots are fetched on demand.

## 4. Package (`package.yml`)
```yaml
package_format: 1
id: acme/ship-to-staging          # publisher/slug, lowercase, stable
kind: pipeline                    # command | folder | pipeline | project | environment | profile
version: 1.2.0                    # semver; prerelease allowed
name: Ship to staging
description: { en: …, pt: … }     # markdown allowed
category: deploy
tags: [git, docker]
author: Acme
license: MIT
homepage: https://…
kai: { min: 1.0.0-beta.2, requires: [pipelines, kip] }
needs: [git, docker]              # external binaries/interpreters, shown in preview
platforms: [linux, macos, windows]
secrets: [REGISTRY_TOKEN]         # names only
media: { icon: icon.png, screenshots: [shot1.png] }
files:                            # payload, each hashed
  - { path: kai.yml, sha256: … }
  - { path: scripts/deploy.sh, sha256: … }
source:                           # kind: project, by reference instead of files
  clone: { url: https://…/app.git, ref: v1.2.0, path: kai.yml }
changelog: CHANGELOG.md
```
- `kai.requires` is a list of **capabilities** (`pipelines`, `kip`, `http`,
  `folder_actions`, …) owned by Kai; a Kai that lacks one greys the package out
  with the reason. `kai.min` is a floor on top.
- `kind: project` has two forms: **bundled** (`files` hold a `kai.yml`) and **by
  reference** (`source.clone`). Exactly one.
- `ref` must be a tag or commit for reproducibility; a branch name is allowed
  but flagged "moves" in the preview.

## 5. Install flow
1. **Detail** — README, screenshots, versions, compatibility, `needs`,
   `secrets`, trust badge, signature state.
2. **Preview** (before anything touches disk) — the tree that will be created,
   every script/command in a read-only code view, interpreters/binaries
   required (with "found / not found"), HTTP URLs the commands call, and the
   decisions below.
3. **Destination** — parent folder in the tree. Name clashes use the existing
   import renaming.
4. **Fetch** — HTTPS only (or local path for `file`); each file's `sha256`
   verified; archive entries rejected on path traversal, absolute paths, size
   limits, or too many entries. For clone-by-reference: `git clone` through
   `QProcess` (async, cancellable), then the existing "import project folder".
5. **Import** — through `config-manager-import` / `project-format`. The package
   content is validated with `kai-file-validator` first; errors block, warnings
   show in the preview.
6. **Record** — provenance (§7). Select the new item.

### Decisions at install (answered in the preview, defaults in bold)
| Feature in the package | Behaviour |
|---|---|
| `hooks` | **Never installed**; listed in the preview as skipped (user can add them by hand) |
| `cron` | **Asked per command**, default off |
| `auto_run` | **Asked per command**, default off |
| KIP autostart | **Asked**, default off |
| `secrets` names | variables created empty; the user fills them in |

Nothing runs at install, regardless of choices.

## 6. API provider
Read-only, JSON, same shapes as §3–§4:
- `GET /v1/store` → header, `GET /v1/index?category=&q=&page=` → index rows,
- `GET /v1/packages/{publisher}/{slug}` → versions + manifests,
- `GET /v1/packages/{publisher}/{slug}/{version}/files/{path}` → a payload file
  (or `…/download` → one archive: `.zip`, same layout).
Auth: optional `Authorization: Bearer <token>`. Unknown fields ignored;
`store_format` greater than the client supports → "update Kai" message.
There is no write endpoint by design.

## 7. Local state
- `store-providers` in settings: the provider list (tokens stored separately,
  `0600`, excluded from export/sync like the AI keys).
- `store-installed.json`: per installation `{ provider, package, version,
  sha256 of payload, folderId, installedAt }`. **Outside `kai.yml`** so that
  versioned project files stay clean; consequence: a project moved to another
  machine is not "tracked" there (accepted).
- Cache dir: index per provider, icons, screenshots; bounded size; a "Clear
  cache" button.

## 8. Update / uninstall
- **Check** only when the Store is open or on "Check for updates". Compares
  `latest compatible` with the installed version.
- **Update** compares the installed payload hash with the folder's current
  content: if the user edited it, the preview says so and offers "Install as a
  copy". There is no merge.
- **Uninstall** removes the tracked folder after a confirmation listing what
  goes (it never touches anything not created by the install).

## 9. Security model
- All Store content is **untrusted code**. The preview is the control point;
  the install itself is inert.
- HTTPS-only for network providers; `sha256` per file; optional **ed25519**
  signature on the index (and on `package.yml` for `official`/`verified`).
  Result states: *signed ok* / *unsigned* / *signature invalid* (blocks install
  for providers that declare a key). The verification needs a primitive Qt does
  not ship: prefer a small vendored implementation (single-file, permissive
  license) to a new heavy dependency — decide with the philosophy's dependency
  test before adding.
- Markdown is rendered sanitized (no raw HTML/script); images only from the
  provider's own origin/path, size-capped, raster formats only.
- Hard limits: index size, package size, file count, per-request timeout, no
  redirects off the provider's host unless it is an allow-listed CDN of the
  same forge.
- Secrets in packages: the validator's existing warning for literal secrets
  turns into an install blocker for `official`/`verified` publishing tools
  (`kai store validate`), a warning for the rest.
- Tokens never sent to a host other than the provider's.

## 10. Publisher tooling (CLI, offline)
- `kai store validate <dir>` — validates `package.yml` + payload (reuses
  `kai validate`), checks hashes, capabilities and media sizes.
- `kai store pack <dir>` — fills `files[].sha256`, optionally writes a `.zip`.
- `kai store index <packages-dir>` — builds `store.yml`'s `index.json` (or the
  single `file` catalog), optionally signs (`--key <file>`).
- `kai store keygen` — makes an ed25519 key pair.
A publisher needs no server and no CI: commit the output to a Git repo and
share the repo URL, or drop one catalog file anywhere.

Repo layout (static):
```
store.yml
index.json
packages/<publisher>/<slug>/<version>/package.yml
packages/<publisher>/<slug>/<version>/kai.yml, scripts/…, icon.png
```

## 11. UI
- **Settings → Store:** provider list as a table (name, kind chip, trust chip;
  pencil/trash) with `+ Add`; the add/edit dialog follows `ParameterRowDialog`
  (name, location, kind, token, trust) with **Test connection**. Section appears
  always; the Store window is reachable only when ≥ 1 enabled provider exists.
- **File → Store…** opens a window (not a grid panel): provider selector,
  category rail, search, grid of cards (icon, name, summary, kind chip,
  version, trust badge), detail view, preview/install dialog. Short texts per
  AGENTS §10; explanations live in docs and Help.
- **CLI:** `kai store list|search|show|install|update`, same preview rules
  (prints what will be created, asks for `cron`/`auto_run`, `--yes` accepts the
  defaults, hooks are never installed).
- **Help topic** `store` and `docs/store.md`; `docs/privacy.md` table gains a
  Store row; `docs/philosophy.md` gains "Not a package manager either".

# Part B — Plan

## 12. Scope for beta.3
In: the three provider kinds, catalog + index + cache, categories, search
(client-side for static), detail, preview, install of every `kind`, clone by
reference, install decisions (§5), provenance, manual update check, ed25519
signing/verification, `kai store` CLI and publisher tools, Settings, window,
docs, Help, manifesto/schema for `package.yml`, tests.
Later: API server reference implementation, dependencies between packages,
diff view on update, screenshot carousel beyond one image, clone-the-whole-repo
provider.

## 13. Code map (proposed)
- `src/core/store-model.{h,cpp}` — `StoreProvider`, `StoreIndex`,
  `StorePackage`, manifest parse/validate, semver + capability matching.
- `src/core/store-installed.{h,cpp}` — provenance file.
- `src/engine/store-provider.{h,cpp}` — abstract `StoreProvider`; `FileProvider`,
  `RepoProvider`, `ApiProvider`; async via `QNetworkAccessManager`/`QProcess`.
- `src/engine/store-installer.{h,cpp}` — fetch, verify, extract, clone, hand
  the content to the importer; progress/cancel signals.
- `src/engine/store-signature.{h,cpp}` — canonical body + ed25519 verify.
- `src/cli/` store verbs; `src/ui/features/store/` window, cards, detail,
  preview dialog, providers table + dialog.
- i18n in `en.json` + `pt.json`; token radii; no hardcoded strings.

## 14. Tests
- Model: manifest/index parse, bad input, semver and capability matching,
  incompatible-version greying, latest-compatible selection.
- Providers (fake local HTTP server + temp dirs): file, repo-over-raw, repo
  clone fallback, API; ETag cache; timeouts; oversize; redirect off-host;
  token not leaked to other hosts.
- Installer: hash mismatch blocks, zip-slip rejected, hooks skipped, cron/
  auto_run/KIP autostart default off and honoured when accepted, secrets created
  empty, conflict renaming, clone by reference (local bare repo), cancel.
- Signature: valid, tampered body, wrong key, unsigned vs declared key.
- Update/uninstall: edited-copy detection, "install as copy", uninstall removes
  only tracked items.
- Validator: package manifest rules; `test_manifestos`/`test_field_scopes` kept
  in sync; `test_i18n_sync`; UI render test with screenshots for the Store
  window, preview and providers dialog.

## 15. Sample: `sample/store/` (file-based, offline)
A working provider that needs no network, so the feature can be tried and
tested end to end:
```
sample/store/
  README.md                      # how to add it: Settings → Store → + Add → this folder's catalog.yml
  catalog.yml                    # kind: file — header + inline packages, relative payload paths
  packages/
    demo/hello-command/1.0.0/    # kind: command   (package.yml, kai.yml)
    demo/ship-to-staging/1.0.0/  # kind: pipeline  (reuses the sample/pipeline payload; cron/auto_run to exercise the questions)
    demo/api-starter/1.0.0/      # kind: folder    (HTTP commands)
    demo/app-by-reference/1.0.0/ # kind: project   (source.clone → a local bare repo created by a script)
  tools/make-clone-fixture.sh    # builds the local bare repo used by app-by-reference
  signed/                        # same catalog signed with a throwaway test key (public key in the header)
```
Includes one deliberately incompatible package (`kai.requires` a capability
Kai lacks) and one with a bad hash, to see the greyed-out and blocked states.
The tests install from this sample.
