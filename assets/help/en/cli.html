CLI — Kai in the terminal

The same kai binary works three ways in the terminal:

Local CLI Pathsinside a folder with a kai.yml, runs the commands from that file — Kai doesn't need to be open
Global CLI Pathsoutside those folders (or with -g), runs the commands with a CLI path registered in the app
Instance controlkai run, kai ps, kai env... talk to the running Kai

1. Giving a command a CLI path

Only items with a CLI Path show up in the terminal (a field in the command and folder editors, or cli_path in the file). Each folder with a path becomes a segment; the command is always the last one:

folders:
  - path: Docker
    cli_path: docker
commands:
  - name: Start container
    folder: Docker
    cli_path: up
    type: command
    command: docker compose up -d {{service}}
    params:
      - name: service
        type: text
      - name: build
        type: bool
        optional: true

That becomes kai docker up api --build=true. Folders without a CLI path are transparent: they aren't a segment, but their children with their own path are still reachable through the folder above.

2. Discover and run

kailists the paths available at the root
kai dockerincomplete path: lists the subfolders and, for each command, its description, usage line and every parameter (required or optional, choices, default and description)
kai docker up apiruns the command
kai docker up --helpshows the command's usage, description and parameters without running anything

Parameters: required ones are positional, in the order they were defined; optional ones only go in as --name=value and fall back to their default when omitted. bool, number and fixed-option select types are validated before running.

Exit code: 0 success; when the command fails, its real code (e.g. 127, 130 on Ctrl+C; 1 when there's none, as in an HTTP request); 2 usage error (unknown path, missing or invalid parameter) — usable in scripts and CI.

3. Local vs. global

Local — there's a kai.yml in the current directory. Only the paths from that file are listed and run. The command is executed from the file's definition: the template is rendered and run straight in the system shell (bash on Linux, cmd.exe on Windows — or the distro itself when kai.exe is called from a WSL folder). Terminal targets and other app-side settings are ignored; the only thing taken from the app is the active Environment's variables. The command uses your terminal directly: interactive prompts, colors and Ctrl+C work like any regular command — which is why responders, open_last_link and compact_output don't apply here. It isn't registered in the app.

Global — with no file in the current directory, kai resolves against the folders and commands registered in the app (anything with a CLI path) and runs them through the app itself: they show up in the process list (kai ps), the history and the output panel, with the terminal target (including the default one), saved dynamic variables and the active Environment. Output comes back to the terminal and what you type goes to the command (Ctrl+C included). If Kai is closed, it's opened in the tray automatically — never as a second instance. Closing the terminal doesn't stop the command: it keeps running in the app (kai kill stops it). An is_background command is just started, and kai hands the terminal back with its PID. To use the global ones from inside a folder with a local file, use the -g flag (or --global), always before the path.

Working directory

A command runs in its own working directory by default, even when started from the terminal. To run it where you typed kai instead (handy for a global git command), tick Run in the directory I invoked it from in the command's CLI Interface tab — or set "cli_working_dir": "invocation" in the file. It applies to local and -g runs and shows in --dry-run; runs started from the Kai window are not affected.

Flags

-g, --globaluses the app's paths even inside a folder with a kai.yml
-d, --detachedstarts it and hands the terminal back right away. In global mode the app registers and runs it (follow with kai attach, stop with kai kill); in local mode the command runs in the background and its output goes to a log file, whose path is shown
-n, --notifytray notification when the command finishes, with how long it took (combines with -d: kai -dn …)
--dry-runshows what would run — the rendered command (parameters, variables, {% if %}), directory, terminal target and hooks — without running it
--jsonlisting and --dry-run as JSON, for scripts (kai --json docker | jq)

Short flags combine (-gdn) — kai -gd docker up api is the same as kai --global --detached docker up api. Flags go before the path; whatever comes after it belongs to the command.

The names run, list, env, show, help, import, validate, ps, attach, kill, raise, history, last, init and completion are reserved and can't be used as a CLI path — kai validate warns about that and about duplicate paths.

4. Controlling the running Kai

These verbs talk to the open instance (with Kai closed they exit with code 2). The command runs inside the app, with all of its settings — terminal target, dynamic variables, history and the process list:

kai run "Deploy"runs a command by name
kai listlists the commands
kai env listlists the environments
kai env use Prodactivates an environment
kai ps [--json]lists the running processes (name, PID, status)
kai attach <pid|name>follows in the terminal the output of a process that's already running (replays what it already printed, then goes live); the keyboard goes to the process, and Ctrl+] releases the terminal without stopping it
kai history [N] [--json]latest runs recorded by Kai (status and duration) — no running Kai needed
kai last [--log] [--json]the most recent run; --log shows its output
kai init [--json] [--force]creates a kai.yml in the current folder from whatever is detected (package.json, docker-compose.yml, Makefile, pyproject…), CLI paths included; with nothing detected, an example to edit
kai kill <pid|name>terminates a process
kai import [file|folder] [--only a,b]imports the kai.yml as a project (no argument: looks in the current folder). A file with the kai_export header (an exported package) is imported whole and without questions — commands, actions, collections, profiles, environments — or only the parts named in --only: commands, collections, settings, environments, terminal-profiles, actions
kai raise --level error "it broke"shows a notification in Kai's tray — levels info (default), warning and error; --title sets the title. Also kept in the notification history. Handy at the end of scripts
kai showbrings the window to the front

No running Kai needed: kai validate <file> checks a kai.yml (structure, duplicate or reserved CLI paths) and exits with 1 on errors. kai help prints a summary of all of this.

Autocomplete (Tab)

Tab completes paths, verbs, --option= and select/bool values — in local and global mode (including after -g). The first time Kai runs in an interactive terminal it asks once whether to turn this on for that terminal (bash, zsh, PowerShell, each WSL distro) and lists what it would write; say no and it never asks again. Nothing is written without a yes.

kai completion install [bash|zsh|powershell|pwsh]   # turn it on by hand
kai completion uninstall [shell]                    # remove it (and remember the "no")
kai completion bash|zsh|powershell                  # just print the script

Bash gets two small files under ~/.local/share/bash-completion/completions/ (no .bashrc edit); zsh and PowerShell get a block marked # >>> kai completion >>> in ~/.zshrc / your $PROFILE. From WSL with the Windows kai.exe, answer the question once and Kai writes into that distro.

A folder can have a CLI description (CLI Interface tab of the folder editor, or cli_description in the file) — it's shown next to the path when kai lists the folder. For commands, the CLI Interface tab holds the path and the description used in the listing and in --help.

Windows and WSL

On Windows the installer puts a small console program, kai.com, next to kai.exe. Typing kai in a terminal runs it first (.com comes before .exe in PATHEXT): it calls kai.exe with the same arguments, waits for it and returns the same exit code. That makes the output show up in every terminal (terminals that host the shell in a pseudo-console, such as the JetBrains IDEs, left kai.exe's output blank), and the prompt only returns when the command ends. Shortcuts and the tray keep using kai.exe.

To use the Windows Kai from WSL, add a shortcut such as alias kai='kai.exe'. Called from a WSL folder, local mode runs the command inside that same distro (through wsl.exe, with {{PROJECT_PATH}} in Linux form), just like a native Kai. Global mode follows the terminal target configured in the app.
