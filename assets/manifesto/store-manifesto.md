# Kai Store manifesto: how to create a store

Read this whole guide before creating a Kai Store. It tells an assistant (or a person) how to publish packages (commands,
folders, pipelines, projects, environments, profiles) that Kai users can install from **File → Store…**.

A store is **not a server**. It is a set of plain files that any *provider* can serve: a Git repository, one catalog file,
or a small HTTP API. Nothing runs when someone installs a package; installing is an import.

## 1. The rules

1. A package is self-contained: no dependencies between packages, no install scripts.
2. Everything is YAML (JSON is also accepted for the index and catalog). No comments are kept by `kai store pack`.
3. Every payload file has a `sha256` in `package.yml`. `kai store pack` computes them; never type a hash by hand.
4. `hooks` in a package are **never installed**. `cron_expression` and `auto_run` are asked per command and start off.
5. Secrets are listed by **name** in `secrets:`; Kai creates them empty. Never put a real token in a package.
6. Paths in `files:` are relative, use `/`, and never contain `..` or start with `/`.
7. Network providers must use HTTPS (plain `http` only for `localhost`).

## 2. Pick a provider kind

| Kind | Use when | What you publish |
|---|---|---|
| Git repo | you already use GitHub/GitLab/any Git host | the files below, committed |
| File | one catalog file is enough (a gist, a static host, a shared folder) | one `.yml`/`.json` listing every package |
| API | you want a server, a token, or dynamic content | the same documents behind `GET /v1/store` and `GET /v1/index` |

The user adds it in **Settings → Store → Add** (name, location, type, optional token, trust label).
For a Git repo the location is `https://github.com/owner/repo` (add `#tag` to pin a ref). Kai reads `store.yml` from the
repo root and, if it is not there, from a `dist/` folder.

## 3. Layout

```
store.yml                                           # catalog header
index.json                                          # generated by `kai store index`
packages/<publisher>/<slug>/<version>/package.yml
packages/<publisher>/<slug>/<version>/kai.yml       # the payload
packages/<publisher>/<slug>/<version>/scripts/...   # more payload files
packages/<publisher>/<slug>/<version>/icon.png      # optional media
```

### 3.1 store.yml

```yaml
store_format: 1
name: Acme Kai Store
description: { en: "Acme tools for Kai", pt: "Ferramentas da Acme para o Kai" }
homepage: https://example.com
categories:
  - { id: deploy, name: { en: Deploy, pt: Deploy }, icon: rocket }
signing: { algorithm: ed25519, key: "<base64 public key>" }   # optional, see section 5
```

`store_format` must be `1`. `categories[].icon` is a Lucide icon name (see the icons reference).

### 3.2 package.yml

```yaml
package_format: 1
id: acme/ship-to-staging          # publisher/slug: lowercase letters, digits, - _ .
kind: pipeline                    # command | folder | pipeline | project | environment | profile
version: 1.2.0                    # semver; a prerelease (1.0.0-beta.1) is allowed
name: Ship to staging
description: { en: "Markdown **allowed**, no HTML", pt: "..." }
category: deploy
tags: [git, docker]
author: Acme
license: MIT
homepage: https://example.com/ship
kai: { min: 1.0.0-beta.2, requires: [pipelines] }
needs: [git, docker]              # programs the content uses (shown in the preview as found / not found)
platforms: [linux, macos, windows]
secrets: [REGISTRY_TOKEN]         # names only
media: { icon: icon.png, screenshots: [shot1.png] }
files:                            # written by `kai store pack`
  - { path: kai.yml, sha256: "<64 hex>" }
```

- `kai.requires` capabilities: `http`, `pipelines`, `kip`, `folder_actions`, `hooks`, `cron`, `collections`, `notes`, `responders`.
  A Kai without one greys the package out with the reason.
- Media files (icon, screenshots) are PNG/JPG/WebP/GIF only, each under 2 MB. They are not listed in `files:`.
- The description is Markdown. Relative images work (`![](shot1.png)` next to `package.yml`).

### 3.3 kinds and payload

| kind | payload `kai.yml` is | result |
|---|---|---|
| command, folder, pipeline | a normal project file (same format as any `kai.yml`) | a folder with its commands |
| project | a normal project file, or **by reference** (3.4) | a project folder |
| environment | a configuration package: `kai_export` header + `settings.environments` | environments added |
| profile | a configuration package with `settings.terminal_profiles` | execution profiles added |

The payload `kai.yml` must pass `kai validate` (read the kai manifesto for the format). A pipeline calls other commands by
**name/path** (`steps/Build`), so ship those commands in the same `kai.yml`.

Environment package example:

```yaml
kai_export: { scope: global, version: 1 }
settings:
  environments:
    - id: env_acme_staging
      name: Acme staging
      vars: { API_URL: "https://staging.acme.example" }
      secret_keys: [API_TOKEN]
```

### 3.4 project by reference (no copy of the content)

A store can contain only links to other repositories that already have a `kai.yml`:

```yaml
package_format: 1
id: me/my-app
kind: project
version: 1.0.0
name: My app
source:
  clone:
    url: https://github.com/me/my-app.git
    ref: v1.0.0          # a tag or commit; a branch works but the preview warns it "moves"
    path: kai.yml        # path of the kai.yml inside the repo (default kai.yml)
```

Use **either** `files:` **or** `source.clone`, never both. Kai makes a shallow `git clone` at install time and the project
points at that clone. This `package.yml` is the only file the store needs for that app.

## 4. Publish workflow

1. Create `store.yml` (3.1).
2. For each package version create the folder `packages/<publisher>/<slug>/<version>/` with `package.yml` (without `files:`)
   and the payload files.
3. `kai store pack <package-dir>` fills `files:` with the hashes. Run it again after **any** payload change.
4. `kai store validate <package-dir>` must report no errors (warnings such as "not listed in files" mean you forgot `pack`).
5. `kai store index <repo-dir>` writes `index.json` (or `--catalog catalog.yml` for a single-file provider, which reads the
   header from `store.yml`).
6. Commit and push. Share the repo URL (Git), or the catalog file URL/path (File).
7. To release a new version, add a **new** folder `.../<new-version>/` and run `pack`, `validate` and `index` again; keep old
   versions so users can still see them.

An update is offered when the index lists a newer **compatible** version than the one installed.

## 5. Signing (optional)

`kai store keygen keyfile` writes a private key file and prints the `signing:` block for `store.yml`. Then
`kai store index <repo-dir> --key keyfile` signs the index. Kai verifies it: a provider that declares a key but serves a missing
or wrong signature **blocks installs**. The signature covers each `package.yml` hash, which covers its files. Keep the key file
out of the repository.

## 6. Recipes

### 6.1 A Git repository store

Follow section 4 in a new repo and push it. Add `https://github.com/<you>/<repo>` as a Git repo provider.
If you prefer a build folder, put `store.yml`, `index.json` and `packages/` under `dist/`; Kai finds it there.

### 6.2 A single catalog file

Run `kai store index <repo-dir> --catalog catalog.yml`. The file has the header plus `packages:` and can sit anywhere. Add its
path or URL as a File provider. Manifests are resolved relative to the catalog's folder.

### 6.3 A store of links to other repos

For each app repo that already has a `kai.yml`, add one `package.yml` with `source.clone` (3.4) and run `kai store index`.
Nothing from those repos is copied into the store.

### 6.4 An API

Serve `GET /v1/store` (the `store.yml` content), `GET /v1/index` (the `index.json` content) and the package files under the paths the
index gives in `manifest`. With a token, require `Authorization: Bearer <token>` and answer 401 otherwise. Kai sends the token only to
that host. A ready example is `sample/store-api/server.py`.

## 7. Checklist

- [ ] `id` is `publisher/slug`, lowercase; `version` is semver.
- [ ] `kind` matches the payload; `project` uses `files:` or `source.clone`, not both.
- [ ] `kai.requires` lists every capability the content uses; `needs:` lists every program it calls.
- [ ] Secrets are names in `secrets:`, never values.
- [ ] No `hooks` you rely on (they are skipped); schedules and auto-run are optional extras.
- [ ] `kai store pack` was run after the last edit; `kai store validate` is clean; `kai store index` was re-run.
- [ ] Description and `summary` have `en` (and `pt` if you have it).
