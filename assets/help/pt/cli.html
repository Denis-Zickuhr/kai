CLI — o Kai no terminal

O mesmo binário kai funciona de três jeitos no terminal:

CLI Paths localdentro de uma pasta com kai.json/kai.yml, roda os comandos daquele arquivo — sem precisar do Kai aberto
CLI Paths globalfora dessas pastas (ou com -g), roda os comandos com caminho de CLI cadastrados no app
Controle da instânciakai run, kai ps, kai env... falam com o Kai em execução

1. Dando um caminho de CLI a um comando

Só aparece no terminal o que tiver um Caminho de CLI (campo no editor de comando e de pasta, ou cli_path no arquivo). Cada pasta com caminho vira um segmento; o comando é sempre o último:

folders:
  - path: Docker
    cli_path: docker
commands:
  - name: Subir container
    folder: Docker
    cli_path: up
    type: command
    command: docker compose up -d {{servico}}
    params:
      - name: servico
        type: text
      - name: build
        type: bool
        optional: true

Isso vira kai docker up api --build=true. Pastas sem caminho de CLI são transparentes: não viram segmento, mas os filhos delas com caminho próprio continuam alcançáveis pela pasta de cima.

2. Descobrir e rodar

kailista os caminhos disponíveis na raiz
kai dockercaminho incompleto: lista as subpastas e, para cada comando, a descrição, a linha de uso e cada parâmetro (obrigatório ou opcional, opções, padrão e descrição)
kai docker up apiroda o comando
kai docker up --helpmostra uso, descrição e parâmetros do comando, sem rodar nada

Parâmetros: os obrigatórios são posicionais, na ordem em que foram definidos; os opcionais só entram como --nome=valor e, se omitidos, usam o valor padrão. Tipos bool, number e select com opções fixas são validados antes de rodar.

Código de saída: 0 sucesso; se o comando falhar, o código real dele (ex.: 127, 130 no Ctrl+C; 1 quando não há um, como numa requisição HTTP); 2 erro de uso (caminho inexistente, parâmetro faltando ou inválido) — dá pra usar em scripts e CI.

3. Local × global

Local — há um kai.json, kai.yml ou kai.yaml no diretório atual. Só os caminhos desse arquivo são listados e rodados. O comando é executado a partir da definição do arquivo: template renderizado e rodado direto no shell do sistema (bash no Linux, cmd.exe no Windows — ou a própria distro, quando o kai.exe é chamado de uma pasta do WSL). Alvos de terminal e demais ajustes feitos no app são ignorados; a única coisa do app que entra são as variáveis do Environment ativo. O comando usa o seu terminal direto: prompts interativos, cores e Ctrl+C funcionam como num comando comum — por isso auto-responsores, open_last_link e compact_output não se aplicam aqui. Não fica registrado no app.

Global — sem arquivo no diretório atual, kai resolve contra as pastas e comandos cadastrados no app (qualquer um com caminho de CLI) e roda pelo próprio app: aparece na lista de processos (kai ps), no histórico e no painel de saída, com alvo de terminal (inclusive o padrão), variáveis dinâmicas salvas e Environment ativo. A saída volta pro terminal e o que você digita vai pro comando (inclusive Ctrl+C). Com o Kai fechado, ele é aberto na bandeja sozinho — sem nunca abrir uma segunda instância. Fechar o terminal não para o comando: ele segue no app (kai kill para). Um comando is_background só é disparado, e o kai devolve o terminal com o PID. Para usar os globais de dentro de uma pasta com arquivo local, use a flag -g (ou --global), sempre antes do caminho.

Flags

-g, --globalusa os caminhos do app mesmo dentro de uma pasta com kai.json/kai.yml
-d, --detacheddispara e devolve o terminal na hora. No global, o app registra e roda (acompanhe com kai attach, pare com kai kill); no local, o comando roda em segundo plano e a saída vai para um arquivo de log, cujo caminho é mostrado
-n, --notifynotificação na bandeja quando o comando terminar, com o tempo que levou (combina com -d: kai -dn …)
--dry-runmostra o que seria executado — comando já renderizado (parâmetros, variáveis, {% if %}), diretório, alvo de terminal e hooks — sem executar
--jsonlistagem e --dry-run em JSON, pra scripts (kai --json docker | jq)

As curtas combinam (-gdn) — kai -gd docker up api é o mesmo que kai --global --detached docker up api. As flags ficam antes do caminho; o que vem depois dele é do comando.

Os nomes run, list, env, show, help, import, validate, ps, attach, kill, raise, history, last, init e completion são reservados e não podem ser usados como caminho de CLI — o kai validate avisa sobre isso e sobre caminhos duplicados.

4. Controlando o Kai em execução

Estes verbos falam com a instância aberta (com o Kai fechado, saem com código 2). O comando roda dentro do app, com todas as configurações dele — alvo de terminal, variáveis dinâmicas, histórico e lista de processos:

kai run "Deploy"executa um comando pelo nome
kai listlista os comandos
kai env listlista os environments
kai env use Prodativa um environment
kai ps [--json]lista os processos em execução (nome, PID, status)
kai attach <pid|nome>acompanha no terminal a saída de um processo que já está rodando (mostra o que ele já imprimiu e segue ao vivo); o teclado vai pro processo, e Ctrl+] solta o terminal sem pará-lo
kai history [N] [--json]últimas execuções registradas pelo Kai (status e duração) — não precisa do Kai aberto
kai last [--log] [--json]a execução mais recente; --log mostra a saída dela
kai init [--json] [--force]cria um kai.yml na pasta atual a partir do que for detectado (package.json, docker-compose.yml, Makefile, pyproject…), já com caminhos de CLI; sem nada detectado, um exemplo pra editar
kai kill <pid|nome>encerra um processo
kai import [arquivo|pasta]importa o kai.json/kai.yml/kai.yaml como projeto (sem argumento, procura na pasta atual)
kai raise --level error "deu pau"mostra uma notificação na bandeja do Kai — níveis info (padrão), warning e error; --title troca o título. Fica também no histórico de notificações. Útil no fim de scripts
kai showtraz a janela à frente

Não precisa do Kai aberto: kai validate <arquivo> confere um kai.json/kai.yml (estrutura, caminhos de CLI duplicados ou reservados) e sai com 1 se houver erros. kai help mostra o resumo de tudo isto.

Autocomplete (Tab)

Com o script instalado, Tab completa caminhos, verbos, --opcao= e valores de select/bool — no modo local e no global (inclusive depois de -g). Coloque no seu ~/.bashrc (funciona também com uma função kai que chama o kai.exe):

eval "$(kai completion bash)"     # zsh: eval "$(kai completion zsh)"

No PowerShell: kai completion powershell | Out-String | Invoke-Expression (no $PROFILE).

Uma pasta pode ter Descrição de CLI (aba Interface CLI do editor de pasta, ou cli_description no arquivo) — ela aparece ao lado do caminho quando o kai lista a pasta. Nos comandos, a aba Interface CLI reúne o caminho e a descrição usada na listagem e no --help.

Windows e WSL

Para usar o Kai do Windows a partir do WSL, crie um atalho, por exemplo alias kai='kai.exe'. Chamado de uma pasta do WSL, o modo local roda o comando dentro da mesma distro (via wsl.exe, com {{PROJECT_PATH}} no formato Linux), igual a um Kai nativo. O modo global segue o alvo de terminal configurado no app.
