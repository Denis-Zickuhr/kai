Python, Node e PHP

O texto de um comando pode ser código em vez de uma linha de shell. Escolha a Linguagem no canto superior direito do campo do comando: Nativa (shell) (o padrão), Python, Node ou PHP. Sem python3 -c "...", sem heredoc: você escreve o código, o Kai monta a chamada.

import os
for f in os.listdir('.'):
    print(f, os.path.getsize(f))

Como roda

O Kai entrega o código ao interpretador codificado, então não há problema de aspas (qualquer aspa, $, crase ou quebra de linha funciona) e o stdin continua livre: o input() funciona e o KIP também. A chamada é só mais uma linha de shell, então passa pelos perfis de execução, como o WSL.

  • A saída do Python é sem buffer e em UTF-8 — não há flush para esquecer.
  • O código Node roda dentro de uma função async: await no topo funciona e return encerra o script. Um erro não tratado sai com código 1.
  • O PHP roda por php -r; um <?php no início é aceito e ignorado. Um namespace ou declare(strict_types=1) no topo do código funciona.
  • O código de saída decide o sucesso como sempre (sys.exit(3), process.exitCode = 3, exit(3)).

Variáveis e parâmetros

O {{VAR}} colide com código de verdade (f"{{x}}", dicionários, template strings do JS), então o código dessas linguagens nunca é interpolado (Python, Node, PHP). Variáveis e parâmetros chegam como variáveis de ambiente, com a precedência de sempre:

import os
print("Publicando em", os.environ["TARGET"])
console.log("Publicando em", process.env.TARGET);

Qual interpretador

  • Configurações → Linguagens guarda os globais: python3, node e php por padrão (no Windows sem perfil de execução, o padrão do Python é python).
  • Um comando pode sobrepor no campo Interpretador.
  • O valor é uma linha de shell resolvida onde o comando roda: num perfil WSL vale o python3 do WSL, e o login shell já carrega pyenv e nvm. Aceita argumentos (uv run python); caminhos com espaço vão entre aspas, por sua conta.

O módulo kai: falar com o app

Todo comando Python/Node tem um módulo kai injetado (nada a instalar) — as mesmas coisas que a CLI kai faz:

import kai
kai.notify("Backup concluído", title="Backup", level="info")   # notificação na bandeja + histórico
kai.commands()              # nomes dos comandos registrados
kai.env.list(); kai.env.active(); kai.env.use("Prod")
kai.run("Deploy")           # dispara outro comando (sem esperar)
kai.ps(); kai.kill("api")   # processos rastreados: {id, name, pid, status}
kai.show()                  # traz a janela para frente
kai.import_project("/caminho/do/kai.yml")
await kai.notify('Backup concluído', { title: 'Backup', level: 'info' });
console.log(await kai.commands(), await kai.env.active());
await kai.env.use('Prod');
await kai.run('Deploy');

No Node, kai é um global (e require('kai')) e toda chamada devolve uma promise. Falhas levantam kai.Error. O Kai exporta KAI_IPC_SOCKET; quando o socket não é alcançável (script no WSL sob um Kai do Windows) o módulo cai para a CLI kai em notify, show, run, env.use e kill.

O módulo kip: transformar o comando num app

Com o KIP ligado, o texto do comando é o programa inteiro e um módulo kip também é injetado (import kip; no Node o global kip; no PHP a classe Kip):

import kip
v = kip.prompt([{"name": "env", "type": "select", "options": ["dev", "prod"]}],
               id="where", title="Para onde?")
kip.progress(50, "Publicando...")
kip.done(title="Publicado em " + v["env"])
$v = Kip::prompt([['name' => 'env', 'type' => 'select', 'options' => ['dev', 'prod']]],
                 ['id' => 'where', 'title' => 'Para onde?']);
Kip::progress(50, 'Publicando...');
Kip::done('Publicado em ' . $v['env']);

Voltar levanta kip.Back (KipBack no PHP), Cancelar sai com código 130, o hello é enviado por você. Referência completa em KIP. Sem o KIP o módulo continua existindo e diz o que ligar quando você o usa. O PHP não tem módulo kai.

Scripts que você roda como arquivo

Os módulos acima são injetados no código de um comando Python/Node/PHP. Um script que roda como arquivo — o seu tool.py, chamado por um comando Nativo com KIP ligado (python3 tool.py, node tool.js, php tool.php) — não passa por esse bootstrap, então o Kai entrega os mesmos módulos pelo disco. Ele os mantém numa pasta própria na pasta temporária (kai-run/modules-…) e exporta onde estão, na frente do que você já tiver nessas variáveis:

  • Python: PYTHONPATH → import kip, import kai.
  • Node: NODE_PATH → require('kip'), require('kai'). Só CommonJS: o import de módulos ES ignora o NODE_PATH.
  • PHP: PHP_INI_SCAN_DIR → a classe Kip já está lá, sem require. O php -r não a lê: use require getenv('KAI_MODULES') . '/kip.php';.
  • Qualquer um: KAI_MODULES é a própria pasta.

Só um comando Nativo com KIP ligado os recebe, para que um pacote kai ou kip do seu próprio projeto nunca seja sombreado por um comando de shell que não pediu o KIP (comandos Python/Node/PHP sempre os têm). Eles não atravessam um perfil de execução (WSL, Docker, SSH): lá as variáveis não são passadas, e o código de um comando Python/Node/PHP continua recebendo os módulos injetados como sempre. Com o KIP desligado, o kip é um substituto que explica o que ligar.

O shell é o Nativo

Não existem linguagens bash, sh ou PowerShell: o Nativo já é um script de shell (bash, e sh onde não há bash), com {{VAR}} e {% if %} substituídos como sempre. Com o KIP ligado, num shell POSIX (Linux, macOS, WSL e outros perfis POSIX), o Kai define uma função kip antes de rodar o texto — os mesmos verbos do kai kip, sem o binário kai:

kip prompt --id p --field text name Nome --required
kip recv                          # a resposta cai em $KIP_MSG
kip done --title "Olá, $(kip get "$KIP_MSG" values.name)!"

Precisa de awk (e base64 + gzip) onde o comando roda. Verbos e limites no KIP, seção 5b. Arquivos antigos com language: bash|sh|pwsh ainda abrem, como Nativo.

Comandos muito longos

Um comando que não cabe na linha de comando do sistema (o cmd.exe do Windows corta em 8191 caracteres; o Linux em uns 128 KB) não exige nada de você: o Kai grava o texto num arquivo próprio na pasta temporária (kai-run, limpa depois de alguns dias) e o roda de lá — o shell para um comando Nativo, o interpretador para Python, Node e PHP. Vale localmente (no Windows também, para Python/Node/PHP) e no WSL. Num perfil WSL as variáveis do ambiente (Global, Pasta, Dinâmicas, Parâmetros — um JWT grande basta) viajam dentro do texto do comando, então também contam: quando a linha mais as variáveis não cabe, o arquivo leva também os exports e a linha vira só . 'arquivo', seja qual for o tamanho do token. O arquivo é legível só por você. Em perfis Docker/SSH, onde esse arquivo não existiria, o comando vai como está (com um aviso se for longo demais).

Limites

Exportar variáveis não se aplica a Python, Node e PHP (não existe export): use o set_env do KIP. O resto — background, hooks, condições, perfis, agendamentos — funciona como em qualquer comando.
